# BUG-20260922-0144: Coding-agent launches cannot reach the internet

## Summary

Sparkplane needs an explicit per-launch internet opt-in without disabling the
coding agent's filesystem sandbox or weakening the appliance's private network.

## Reproduction

On Codex 0.155.1, run from a development checkout:

```sh
codex sandbox -c 'sandbox_mode="workspace-write"' -- \
  curl --fail --max-time 10 https://example.com
```

The command fails with `Could not resolve host: example.com`. Adding
`-c sandbox_workspace_write.network_access=true` succeeds. With Sparkplane's
inherited `SSL_CERT_FILE` pointing at the Spark CA, the network-enabled command
instead fails with `unable to get local issuer certificate`. Using
`CODEX_CA_CERTIFICATE` for that CA succeeds without replacing curl's trust store.

## Expected

`sparkplane dgx-spark launch codex --allow-network` permits network access for
workspace-sandboxed development commands. Default launch permissions are
unchanged. The option also configures Claude's sandbox domain allowlist;
OpenCode already has direct network access and retains its tool permissions.

## Actual

The launcher has no network opt-in and exports a process-wide private trust store.

## Root cause

The launcher directly executes local agents, which own their sandbox policy.
Codex disables network access in its workspace sandbox by default. Additionally,
exporting `SSL_CERT_FILE` to the entire child process tree replaces public CA
trust for development tools. Neither failure is in the GPU engine network.

## Fix

Add invocation-only `--allow-network` / `SPARKPLANE_LAUNCH_ALLOW_NETWORK`.
Use each agent's narrow network setting, leave filesystem and approval policy
alone, and retain managed policy restrictions. Reject configuration-only and
restore combinations rather than silently persisting an access grant. Use
`CODEX_CA_CERTIFICATE` for Codex-specific private CA trust.

## Traceability

- CLI regressions: `tests/standalone_cli.rs`.
- Adapter and CA regressions: `src/spark/launch.rs`, `src/spark/client.rs`.
- Manual verification: the Codex sandbox commands above (no model invocation).

## Verification

- CLI tests cover the flag, environment equivalent, forwarded arguments,
  conflicting Claude settings, and rejection of persistent/restore grants.
- Adapter tests cover default permissions, Codex/Claude network-only overrides,
  unchanged OpenCode permissions, and Codex-specific CA scoping.
- The optional native sandbox regression was executed successfully on Codex
  0.155.1: default DNS is blocked, opted-in public HTTPS returns 200, and attempted
  writes outside the workspace fail in both cases.

```sh
cargo test --locked --lib native_codex_network_opt_in_keeps_filesystem_confinement -- --ignored
make lint
make test
make test-client
make audit
```

The live launch dry-run reused the healthy `qwen38-vllm` instance and reported
`allow_network: true`; the environment-variable form was checked separately.
The production launch path also delivered the scoped CA to a Codex sandbox
diagnostic: HTTPS returned 200 and the workstation configuration remained
read-only. Codex's `sandbox` diagnostic reads subcommand-local configuration,
so this particular probe repeats the network override after `sandbox`; ordinary
TUI/exec launches receive the root-level override directly.
